# Source Repository 기반 온보딩 문서 작성 Skill

## 0. 실행 계약과 독립 배포

`study-material-generator`의 학습 구조와 디자인·구현을 바탕으로 필요한
자원을 이 폴더에 포함했다. **이 스킬 폴더 하나를 복사하거나 링크하면 된다.**
실행 중 다른 스킬을 읽거나 설치할 필요가 없다. 사용자의 요청과 대상
저장소 지침을 우선하고, 온보딩 내용은 이 문서와 내부 참고 문서를 따른다.

### 0.1 시작 조건과 출력 모드

- 입력: 대상 저장소 경로, 필요하면 대상 모듈·핵심 기능, 문서 범위,
  출력 경로와 형식. 먼저 대상 저장소의 `AGENTS.md`와 기존 문서를 읽는다.
- 경로와 범위가 이미 명확하면 분석을 시작한다. 누락된 정보 중 작업에
  필수적인 것만 질문한다. 별도 범위가 없으면 전체 구조를 탐색하고
  12절의 P0부터 작성하며, 제외 범위와 후속 작업을 기록한다.
- **Markdown 모드(기본)**: 기존 문서 경로와 구조를 우선한다. 새 경로가
  필요하면 대상 저장소의 `docs/onboarding/index.md`와 주제별 문서를 만든다.
- **HTML 모드(요청 시)**: 동일한 분석 내용을 단일 `onboarding.html`로
  제공한다. 기본 위치는 대상 저장소의 `docs/onboarding/onboarding.html`이다.
  상세 주제는 파일 대신 챕터로 나누므로 한 페이지에 긴 본문을 몰아넣지 않는다.
- **두 형식 모두 요청 시**: Markdown을 내용의 기준으로 삼고 같은 근거와
  검증 결과를 HTML에 반영한다. 두 형식을 별도로 조사하거나 추론하지 않는다.
- 문서 생성은 배포·롤백·DB 초기화·운영 리소스 변경을 실행하는 요청으로
  해석하지 않는다. 명령 검증은 요청 범위와 대상 환경에서 허용되는 작업에
  한하며, 실행하지 못한 항목은 이유와 함께 남긴다.

### 0.2 내부 자원 로드와 의존성

내용을 작성하기 전에 아래 내부 참고 문서를 읽는다.
경로는 **이 SKILL.md가 있는 디렉터리 기준**이며 분석할 저장소 기준이 아니다.

- [content-structure.md](references/content-structure.md):
  학습 목표, 도입 동기, 본문·요약·Q&A, 다이어그램 해설 규칙을 재사용한다.
- HTML 모드에서는 추가로
  [design-tokens.md](references/design-tokens.md),
  [interactions.md](references/interactions.md),
  [template.html](assets/template.html)의 실제
  스키마와 렌더링 코드를 읽는다. 문서와 구현이 다르면 기존 템플릿 동작을
  확인하고 임의로 CSS/JS를 다시 만들지 않는다.

Markdown 생성 자체에는 Python이나 브라우저 라이브러리가 필요 없다.
HTML 모드는 내부 템플릿을 사용하고, 검증·오프라인 번들에는 Python 3
표준 라이브러리를 사용한다. `assets/vendor/`에는 템플릿 버전에 맞는
Mermaid·D3 캐시가 포함되어 있으므로 기본 템플릿의 오프라인 번들 생성에는
다운로드가 필요 없다. 새 라이브러리를 추가하거나 캐시를 삭제한 경우의
네트워크 요구는 별도로 확인한다.

유지보수 시 기반 스킬의 변경 사항 중 필요한 것을 수동으로 반영하고
내부 참고 문서·템플릿·스크립트를 함께 검증한다. 기반 스킬 변경이 이
패키지에 자동 반영되지는 않는다. 배포에는 `assets/`, `references/`,
`scripts/`를 포함한 디렉터리 전체가 필요하다.

### 0.3 기반 스터디 규칙을 온보딩에 적용하는 방식

| 부모 규칙 | 온보딩 적용 방식 |
|---|---|
| 표준/RFC/논문 중심 근거 | 프로젝트 동작은 실제 소스·설정·테스트·실행 결과가 우선이다. 외부 자료는 해당 버전의 기술 동작 설명을 보완할 때 사용한다. |
| 모든 기술에 대안 비교표 | ADR에 기록된 선택 또는 요청한 비교에 적용한다. 기록되지 않은 선택 이유를 만들어내지 않는다. 일반 기능·설정·API 목록은 보통 표로 작성한다. |
| 비즈니스·비용 정보 제외 | 확인된 업무 의미, 사용자 가치, 운영 비용 제약은 온보딩에 포함할 수 있다. 저장소나 제공 자료에서 근거를 찾지 못하면 확인 필요로 남긴다. |
| 모든 개념을 표준 수준까지 설명 | 핵심 작업을 이해하고 수행할 깊이로 정의·작동 원리·사용 이유를 설명한다. 관련 없는 비트필드·수식·프로토콜 강의를 추가하지 않는다. |
| 프로덕션·클라우드 구성 필수 | 실제 소스·배포 설정·IaC 또는 제공된 운영 자료에서 확인한 구성만 설명한다. 존재하지 않는 LB·NAT·클라우드 리소스를 보충하지 않는다. |
| 모든 수치에 외부 각주 | 버전·포트·타임아웃·재시도 횟수는 설정 위치로 입증한다. 성능 수치는 측정 조건·시점·결과로 입증하고 외부 벤치마크와 프로젝트 측정을 구분한다. |
| 단일 study.html | 기본 Markdown 문서 묶음을 유지하고 HTML 요청 시 onboarding.html을 생성한다. |
| UI·검색·용어집·다이어그램 | HTML 모드에서 내장 템플릿과 디자인·인터랙션을 사용한다. |

### 0.4 근거와 검증 기록

분석 기준 저장소, 브랜치, 확인 가능한 커밋, 분석일, 대상 모듈과 제외
범위를 진입점 문서에 남긴다. 커밋을 확인하지 못하면 그 사실을 기록한다.
작업 트리에 변경이 있으면 커밋만으로 분석 내용을 재현할 수 없음을 표시한다.

중요한 동작·업무 규칙·설정·다이어그램에는 다음 기록을 연결한다.

| 필드 | 기록 내용 |
|---|---|
| 근거 | 저장소 상대 경로, 심볼·설정 키·테스트명, 필요하면 확인 시점의 줄 번호 |
| 판단 상태 | 확인됨 / 추론 / 확인 필요 |
| 실행 검증 | 통과 / 실패 / 미실행 / 해당 없음, 실행 환경·명령·날짜·사유 |
| 갱신 조건 | 변경되면 재검토할 파일·API·설정·테스트와 관련 문서 |

판단 상태와 실행 검증은 독립적이다. 테스트 파일을 읽어 동작을 확인해도
실행 결과가 없으면 테스트 통과를 주장하지 않는다. 기존 README와 코드가
충돌하면 양쪽 근거와 차이를 남기고 현재 분석 기준 코드의 동작을 설명한다.
서로 다른 환경의 설정을 운영의 실제 적용값으로 단정하지 않는다.

근거 링크는 확인된 저장소 URL이 있으면 분석 커밋의 파일 링크를 사용하고,
없으면 산출물 위치에서 계산한 상대 경로를 사용한다. 로컬 절대 경로를
배포 문서에 넣지 않는다. 단일 HTML은 학습 내용을 담지만 원본 소스까지
포함하지는 않으므로 경로·심볼을 본문에도 표시하고 링크의 접근 조건을 남긴다.

### 0.5 학습 구조와 HTML 매핑

진입점에 확인 가능한 학습 목표를 둔다. 예: 로컬에서 기동하고 헬스 체크를
확인한다; 핵심 기능 하나를 진입점부터 저장까지 추적한다; 변경 대상과
관련 테스트를 찾는다. 완료하지 않은 실행을 학습 목표 달성으로 표시하지 않는다.

핵심 기능 문서는 **왜 알아야 하는가 → 개념·업무 규칙 → 실제 코드 흐름 →
변경·테스트 방법 → 핵심 요약 → 문제 상황 Q&A** 순서로 읽히게 구성한다.
Q&A는 권한 실패, 예외 처리, 데이터 일관성, 환경 오류 등 확인한 조건을
다룬다. 단순 목록이나 짧은 설정 문서에는 이 구성을 억지로 반복하지 않는다.

HTML은 내장 템플릿을 출력 위치로 복사하고 예시 데이터를 모두 교체한다.
기본 편집 대상은 `#content-data`이며 패키지의 원본 템플릿과 스크립트는 수정하지 않는다.

| 온보딩 내용 | 내장 템플릿 JSON 필드 |
|---|---|
| 제목·문서 버전·생성일·실제 검토일 | title, version, createdDate, reviewedDate |
| 작업으로 확인할 학습 목표 | learningGoals |
| 개요, 로컬 실행, 도메인, 핵심 기능, API·데이터, 운영 등 | chapters: id, title, motivation, sections, summary, qa |
| 여러 독립 저장소·서비스의 문서 허브(필요 시) | projects: id, title, icon, chapters |
| 도메인·기술 용어와 코드 명칭 | glossary: term, full, definition, seeIn |
| 소스·설정·테스트·ADR·외부 공식 문서 | references: id, text, url, kind |

- `title`에 수동 챕터 번호를 붙이지 않고 챕터 ID는 전체 문서에서 고유하게
  유지한다. 단일 프로젝트는 `chapters`, 여러 독립 문서 그룹은 `projects`를
  사용한다. 프로젝트별 챕터 목록과 챕터 내부 TOC를 구분한다.
- 소스 근거와 검증 표는 기존 `sections[].html`에 담는다. 새 필드를 추가하면
  자동으로 표시된다고 가정하지 않는다. 문서 버전과 분석 커밋은 구분한다.
  `reviewedDate`에는 실제 검토일만 넣고 미검토 상태는 본문에 표시한다.
- 각주 ID는 고유한 정수로 관리하며 `<sup class="fn" data-ref="1">1</sup>`와
  `references[].id`를 일치시킨다. 소스·설정·테스트는 `kind: informative`,
  실제 규범 문서는 `kind: normative`로 둔다. 지원하지 않는 `kind: source`를
  만들지 않는다. `text`에 경로·심볼·판단 상태를 표시한다.
- 용어집의 `seeIn`은 실제 챕터 ID를 참조한다. 첫 사용에서 약어를 풀어 쓰고
  HTML에서는 `<abbr>` 설명을 제공한다. 업무 용어는 코드 명칭과 연결한다.
- 다이어그램 바로 아래에 `그림 설명: ...`을 넣고 노드·호출·분기와 대응하는
  단계별 해설 및 근거를 제공한다. 동적 호출을 정적으로 확정할 수 없으면
  추론 상태를 유지한다. 긴 흐름은 정상·실패 경로로 나눈다.
- 코드·명령·설정·로그는 HTML 특수 문자를 이스케이프하고 유효한 JSON으로
  직렬화한다. JSON 스크립트 안의 종료 태그는 `\u003c/script>`처럼 처리해
  데이터가 스크립트 블록을 조기에 닫지 않도록 한다. 비밀 값은 복사하지 않는다.

### 0.6 단계별 생성과 모드별 검증

분량이 크면 **전체 목차·근거 목록 → 주제/핵심 기능별 작성 → 용어집·링크
연결 → 최종 검증**으로 나눈다. HTML의 빈 챕터는 작성 중 임시 상태이며
전달 전에 내용을 채우거나 제외 범위로 정리한다. 검증 실패 또는 미검증
항목은 최종 산출물과 사용자에게 함께 알린다.

Markdown은 11절의 체크리스트로 소스 경로·링크·명령·근거를 검토한다.
HTML은 여기에 내장 스키마 검증과 검색·단축키·테마·용어집·다이어그램
동작 확인을 추가한다. 아래 명령은 **이 스킬 저장소 루트에서 실행하는 예시**다.
다른 설치에서는 실제 설치된 이 스킬의 경로를 사용한다. 스킬 폴더에서
실행할 때는 `python scripts/validate-onboarding.py <HTML 경로>`처럼 사용한다.

```bash
python skills/source-onboarding-generator/scripts/validate-onboarding.py <onboarding.html 경로>
python skills/source-onboarding-generator/scripts/bundle-offline.py <onboarding.html 경로> -o <onboarding-offline.html 경로>
```

`validate-onboarding.py`는 JSON·기본 스키마를 검사하지만 소스 설명의 정확성이나
실행 성공을 증명하지 않는다. 누락 각주와 잘못된 용어집 참조가 경고로만
보고될 수 있으므로 종료 코드가 0이어도 경고를 검토·해결한다. 브라우저를
사용할 수 없으면 UI 동작은 미검증으로 남긴다.

오프라인 번들은 요청 시 생성한다. 내장 번들러는 Mermaid·D3를 캐시에서
읽거나 다운로드하고 외부 폰트는 시스템 폰트로 대체한다. 다운로드 실패나
추가 외부 리소스가 있어도 완전 오프라인 성공을 보장하지 않으므로 남은
런타임 의존성과 네트워크 차단 상태의 동작을 확인한다. 외부 근거 링크는
열람에 네트워크·저장소 접근이 필요할 수 있으며 런타임 의존성과 구분한다.
내장 템플릿 인쇄는 현재 열린 챕터만 대상으로 하므로 전체 문서 PDF를
제공했다고 표현하지 않는다.

## 1. Skill 목적

이 문서는 소스 코드 레포지토리를 분석해 신규 개발자가 시스템을 이해하고,
로컬에서 실행하고, 기능을 수정하고, 테스트하고, 배포·운영할 수 있도록
온보딩 문서를 작성하는 표준 절차와 산출물 기준을 정의한다.

대상은 단일 애플리케이션, 모놀리스, 모듈형 모놀리스,
마이크로서비스(MSA), 프런트엔드·백엔드·인프라가 함께 있는 저장소다. 특정
언어나 프레임워크에 종속되지 않되, 저장소에서 확인되는 기술 스택에 맞춰
내용을 조정한다.

### 핵심 원칙

1.  **코드에 근거해 작성한다.** 확인하지 않은 클래스, API, 설정, 리소스,
    실행 명령을 지어내지 않는다.
2.  **사실과 추론을 구분한다.** 코드에서 직접 확인한 내용, 분석을 통한
    추론, 담당자 확인이 필요한 내용을 구별한다.
3.  **소스 위치를 연결한다.** 중요한 설명에는 파일 경로, 클래스, 메서드,
    설정 키, 테스트 파일 등 근거를 기록한다.
4.  **개발자의 작업 경로를 중심으로 구성한다.** 프로젝트 이해 → 로컬
    실행 → 기능 추적 → 변경·테스트 → 배포·운영 순으로 탐색할 수 있게
    한다.
5.  **실제와 문서가 일치하도록 한다.** 문서의 명령과 설정은 가능한
    범위에서 검증하고, 검증하지 못한 경우 그 사실을 명시한다.
6.  **읽기 단위를 분리한다.** Markdown은 진입점(index)과 주제별·기능별
    문서로, HTML은 표지와 주제별·기능별 챕터로 분리한다.
7.  **보안 정보를 노출하지 않는다.** 토큰, 비밀번호, 개인 키, 실제 비밀
    값, 개인정보를 문서에 복사하지 않는다.
8.  **필요한 만큼 문서화한다.** 모든 클래스와 모든 메서드를 나열하기보다
    핵심 개념, 변경 영향, 복잡한 흐름, 운영상 중요한 정보를 우선한다.
9.  **자동 생성 결과를 검토한다.** LLM이 생성한 내용은 컴파일러나
    테스트가 보장하지 않는 의미적 오류가 있을 수 있으므로 검증 상태를
    표시한다.
10. **코드 변경과 문서 갱신을 연결한다.** 어떤 소스 변경이 어떤 문서에
    영향을 주는지 추적할 수 있도록 한다.

## 2. 입력과 분석 범위

### 2.1 우선 확인할 저장소 자료

다음 파일과 디렉터리를 우선 탐색한다. 존재하지 않는 항목은 없는 것으로
처리하고, 해당 기술을 사용한다고 가정하지 않는다.

-   README 및 기존 `docs/`
-   최상위 디렉터리 및 모듈별 디렉터리
-   빌드 파일: `pom.xml`, `build.gradle`, `settings.gradle`,
    `package.json`, lock 파일 등
-   애플리케이션 진입점과 실행 설정
-   설정 파일: YAML, properties, TOML, JSON, 환경별 설정 파일
-   API 정의: OpenAPI, GraphQL schema, proto, 라우팅 설정
-   데이터 모델: ORM 엔티티, SQL, ERD, 마이그레이션 파일
-   테스트: 단위·통합·계약·E2E 테스트
-   배포 파일: Dockerfile, Compose, Kubernetes manifest, Helm chart
-   CI/CD: GitHub Actions, GitLab CI, Jenkinsfile 등
-   IaC: Terraform, CloudFormation, CDK, Pulumi 등
-   메시지 큐, 이벤트, 스케줄러, 배치 설정
-   인증·인가 및 보안 설정
-   로깅, 메트릭, 트레이싱, 헬스 체크 설정
-   ADR, 운영 가이드, 장애 대응 문서
-   코드 소유자, 기여 가이드, 라이선스 및 의존성 관리 파일

### 2.2 분석 순서

1.  저장소의 전체 구조와 기술 스택을 파악한다.
2.  실행 진입점, 빌드·테스트 명령, 환경별 설정을 확인한다.
3.  모듈·패키지·컴포넌트의 책임과 의존성을 추적한다.
4.  API, 이벤트, 스케줄러 등 외부에서 시작되는 진입점을 찾는다.
5.  진입점부터 도메인 로직, 데이터 저장소, 외부 연동까지 호출 경로를
    추적한다.
6.  테스트를 통해 의도된 동작과 예외 조건을 확인한다.
7.  DB 스키마, 마이그레이션, 외부 서비스 및 인프라 리소스를 연결한다.
8.  CI/CD 및 운영 설정에서 빌드·배포·관측·복구 절차를 확인한다.
9.  근거가 부족한 내용은 추정으로 채우지 말고 `확인 필요`로 기록한다.

### 2.3 근거 상태 표시

필요한 경우 문서 또는 내부 검토 메모에 다음 상태를 사용한다.

-   **확인됨**: 소스, 설정, 테스트 또는 실행 결과로 직접 확인
-   **추론**: 여러 코드 근거를 조합해 추론했으나 명시적인 보장은 없음
-   **확인 필요**: 저장소만으로 판단할 수 없으며 담당자나 운영 환경
    확인이 필요
-   **검증되지 않음**: 문서화했지만 실제 실행·배포·운영 검증을 수행하지
    않음

## 4. 필수 문서별 작성 지침

### 4.1 프로젝트 개요

다음을 간결하게 기록한다.

-   프로젝트가 해결하는 문제
-   주요 사용자 및 사용 시나리오
-   시스템의 범위와 범위 밖의 책임
-   핵심 비즈니스 기능
-   주요 외부 연동
-   기술 스택과 실행 방식
-   현재 상태, 중요한 제약, 알려진 문제
-   신규 개발자가 가장 먼저 읽어야 할 문서 링크

비즈니스 설명이 저장소에서 확인되지 않는다면 임의로 만들어내지 말고
담당자 확인 항목으로 분리한다.

### 4.2 아키텍처

아키텍처는 하나의 그림으로 모든 관점을 표현하지 않는다. 필요에 따라
다음을 분리한다.

1.  **시스템 컨텍스트**: 사용자, 시스템 경계, 외부 시스템, 연동 관계
2.  **컨테이너·실행 단위**: 프런트엔드, API, 워커, DB, 캐시, 메시지
    브로커 등
3.  **컴포넌트·모듈**: 패키지, 모듈, 계층, 인터페이스, 의존성 방향
4.  **배포 아키텍처**: 프로세스와 클라우드 리소스, 네트워크, 가용성 구성
5.  **데이터 흐름**: 데이터 생성·변환·저장·전달·삭제 경로
6.  **보안 경계**: 인증·인가 지점, 신뢰 경계, 비밀정보 접근 경로

각 다이어그램에 다음을 덧붙인다.

-   다이어그램의 목적과 범위
-   주요 컴포넌트의 책임
-   통신 방식과 프로토콜
-   데이터 소유권과 트랜잭션 경계
-   장애 격리 및 단일 장애 지점
-   소스·설정·IaC의 근거 위치
-   설계상의 제약과 확인 필요 사항

코드에 근거가 없는 아키텍처 요소를 그림에 추가하지 않는다. 추론으로
작성한 경우 추론임을 표시한다.

### 4.3 기술 스택

기술별로 다음을 기록한다.

  항목            기록 내용
  --------------- -----------------------------------------
  기술명          언어, 프레임워크, DB, 메시지 브로커 등
  버전            빌드 파일·이미지·런타임에서 확인한 버전
  사용 목적       어느 계층이나 기능에서 사용하는가
  사용 위치       설정 파일, 모듈, 주요 패키지
  운영상 주의점   호환성, 업그레이드, 알려진 제약
  근거            파일 경로와 설정 키

버전을 확인할 수 없다면 추정하지 않는다.

### 4.4 Ubiquitous Language / 도메인 용어 사전

용어별로 다음 필드를 정의한다.

-   공식 용어
-   영문 표현과 코드 명칭
-   정확한 정의
-   동의어 또는 혼용 금지 표현
-   관련 용어와 도메인
-   관련 클래스·필드·Enum·테이블
-   관련 비즈니스 규칙
-   확인 상태 및 담당자

`Member`, `Account`, `User`, `Principal`처럼 이름이 비슷해도 의미가 다를
수 있는 개념은 반드시 구분한다. 용어의 의미가 코드만으로 확정되지
않는다면 도메인 담당자 확인 대상으로 둔다.

### 4.5 기능 카탈로그

기능별로 다음 정보를 정리한다.

-   기능 ID와 이름
-   목적과 사용자 가치
-   사용자 또는 시스템 액터
-   진입점: API, 이벤트, 스케줄러, UI 등
-   사전 조건과 권한
-   입력·출력
-   정상 결과와 주요 비즈니스 규칙
-   주요 예외와 실패 조건
-   관련 모듈·클래스·메서드
-   관련 DB·이벤트·외부 시스템
-   관련 테스트
-   관측 방법 및 운영상 주의점
-   관련 문서 링크

기능 ID는 예를 들어 `MEMBER-003`처럼 안정적으로 관리할 수 있다. 기존
명명 규칙이 있다면 이를 우선한다.

### 4.6 기능별 코드 구조

기능마다 실제 호출 경로와 책임을 기록한다. 예를 들어 계층형 Spring Boot
애플리케이션이라면 아래와 같은 후보를 확인하되, 실제 구조가 다르면 코드
구조를 그대로 반영한다.

-   진입점: Controller, Handler, Consumer, Scheduler
-   입력 검증과 인증·인가
-   Application Service / Use Case
-   Domain Model 및 비즈니스 규칙
-   Repository / Persistence Adapter
-   DB·캐시·스토리지
-   외부 API 및 메시지 발행
-   예외 변환과 응답 생성
-   테스트 파일

각 구성 요소에 대해 `파일 경로 → 클래스 → 핵심 메서드 → 책임`을
연결한다. 계층 이름만 나열하지 말고 실제 데이터와 제어가 어떻게 흐르는지
설명한다.

### 4.7 업무 플로우와 시퀀스 다이어그램

**업무 플로우**는 사용자의 목표와 비즈니스 단계, 조건 분기를 설명한다.

**시퀀스 다이어그램**은 시간 순서에 따른 컴포넌트 간 호출과 응답을
설명한다.

시퀀스 다이어그램에는 가능한 한 다음을 포함한다.

-   Actor와 진입점
-   핵심 컴포넌트
-   동기 호출과 비동기 메시지
-   정상 흐름과 주요 분기
-   트랜잭션 경계와 커밋 시점
-   타임아웃, 재시도, 예외 전파
-   멱등성, 중복 요청 방지
-   이벤트 발행·소비 및 보상 처리

모든 메서드 호출을 표현하지 않는다. 핵심 비즈니스 플로우, 복잡한 분기,
데이터 일관성, 장애 처리 경로를 우선한다.

### 4.8 API 문서

API별로 다음을 기록한다.

-   HTTP method와 경로
-   목적과 호출 주체
-   인증·인가 요건
-   Path, Query, Header, Body
-   Request/Response 스키마 예시
-   유효성 검증 규칙
-   상태 코드와 오류 응답 형식
-   페이지네이션·정렬·필터링
-   멱등성 및 중복 요청 처리
-   Rate limit 및 타임아웃 관련 사항
-   관련 Controller·DTO·Service·테스트
-   OpenAPI 문서와의 관계

실제 API 정의가 OpenAPI 등에서 생성되는 경우 원본 명세를 단일 진실
공급원으로 삼고 중복된 수기 문서가 어긋나지 않도록 한다.

### 4.9 데이터 모델

-   ERD와 테이블 간 관계
-   테이블·컬럼의 업무적 의미
-   PK, FK, Unique, Check 등 제약 조건
-   인덱스와 주요 조회 패턴
-   엔티티와 도메인 객체의 차이
-   트랜잭션 범위와 격리 수준(확인 가능한 경우)
-   생성·수정·삭제·보관 정책
-   개인정보·민감정보 분류
-   데이터 보존 및 삭제 정책
-   마이그레이션 도구와 실행 순서
-   롤백 가능 여부와 호환성 주의점

DB에 직접 접근할 수 없거나 운영 스키마를 확인하지 못했다면 코드의 엔티티
정의와 실제 운영 스키마를 혼동하지 않는다.

### 4.10 외부 시스템·이벤트·비동기 처리

외부 연동별로 다음을 기록한다.

-   목적과 소유 시스템
-   호출 방향과 프로토콜
-   인증 방식(비밀 값은 기록하지 않음)
-   요청·응답 또는 이벤트 스키마
-   타임아웃·재시도·백오프
-   Circuit Breaker와 Rate limit
-   중복 전달 및 멱등성 처리
-   순서 보장과 일관성 모델
-   DLQ, 재처리, 보상 처리
-   장애 발생 시 사용자 영향
-   로컬 테스트 방법과 관련 테스트

메시지 기반 시스템에서는 Producer, Broker, Consumer, Retry, DLQ, 재처리
절차를 함께 문서화한다.

### 4.11 설정과 환경 변수

설정 항목별로 다음을 기록한다.

-   설정 키
-   목적과 기본값(확인된 경우)
-   필수 여부
-   적용 환경
-   민감정보 여부
-   값의 공급원: 환경 변수, Secret Manager, Parameter Store 등
-   설정 우선순위
-   관련 코드와 사용 위치
-   누락·오류 시 동작

실제 비밀번호, 토큰, 인증서 개인 키, 고객 데이터는 문서에 넣지 않는다.
샘플에는 안전한 플레이스홀더를 사용한다. 환경별 설정 파일에 중복된 값이
있다면 어느 값이 실제로 우선 적용되는지 확인한다.

### 4.12 빌드와 로컬 실행

다음 항목을 실제 저장소에 맞게 작성한다.

1.  필수 도구와 버전
2.  레포지토리 복제 방법
3.  로컬 설정 준비
4.  DB·캐시·메시지 브로커 등 의존 서비스 기동
5.  스키마 마이그레이션과 테스트 데이터 준비
6.  빌드 명령
7.  테스트 명령
8.  실행 명령과 활성 프로파일
9.  포트와 헬스 체크
10. 디버깅 방법
11. 종료 및 초기화 방법
12. 자주 발생하는 오류와 해결법

명령은 복사해 실행할 수 있도록 코드 블록에 넣는다. 실행하지 않은 명령은
`미검증`으로 표시한다. 프로젝트에 없는 스크립트나 태스크를 가정하지
않는다.

### 4.13 테스트 전략

-   단위 테스트
-   통합 테스트
-   API·계약 테스트
-   E2E 테스트
-   DB·마이그레이션 테스트
-   이벤트·비동기 테스트
-   성능·부하 테스트
-   보안 테스트
-   테스트 데이터와 초기화 방법
-   외부 서비스 대역(mock/stub) 사용 방법
-   CI에서 실행되는 테스트 범위
-   로컬에서 실행하는 명령
-   알려진 불안정 테스트와 제약

테스트가 존재한다는 사실과 테스트가 성공했다는 사실을 구분한다. 실제
실행 결과가 없다면 성공했다고 표현하지 않는다.

### 4.14 CI/CD·배포·롤백

파이프라인 단계별로 다음을 기록한다.

-   트리거: push, MR/PR, tag, 수동 실행 등
-   빌드와 테스트 단계
-   이미지 또는 패키지 생성
-   레지스트리와 아티팩트
-   환경별 배포 대상
-   승인과 권한
-   환경 변수와 시크릿 주입
-   헬스 체크 및 배포 성공 기준
-   점진적 배포 또는 롤링 배포 전략
-   실패 시 처리
-   롤백 절차와 롤백 제한
-   배포 후 검증
-   파이프라인 정의 파일의 경로

DB 스키마 변경, 이벤트 스키마 변경, 외부 API 호환성은 애플리케이션
바이너리 롤백과 별개로 검토한다.

### 4.15 인프라·클라우드 리소스

사용 중인 리소스에 한해 다음을 기록한다.

-   클라우드 계정·프로젝트·리전(민감한 식별정보는 조직 정책 준수)
-   네트워크, 서브넷, 라우팅, 보안 그룹
-   DNS, CDN, 로드 밸런서, WAF
-   컴퓨팅·컨테이너·서버리스 리소스
-   DB, 캐시, 스토리지
-   큐, 토픽, 이벤트 버스
-   IAM 역할과 권한 경계
-   Secrets Manager·Parameter Store 등 설정 공급원
-   로그·메트릭·알람
-   IaC 파일과 모듈 위치
-   네이밍 규칙, 태그, 소유자
-   고가용성, 백업, 복구 및 비용 고려사항

리소스 이름이나 ID가 환경별로 달라지면 하드코딩하지 말고 환경별 매핑을
설명한다. 실제 계정 ID, 공개되지 않아야 할 엔드포인트, 보안 설정 등은
조직 정책에 따라 마스킹한다.

### 4.16 관측 가능성과 장애 대응

-   로그 위치와 조회 방법
-   상관관계 ID / Trace ID
-   주요 메트릭과 대시보드
-   분산 추적 구성
-   헬스 체크 및 readiness/liveness
-   알람 조건과 심각도
-   알람 수신자와 에스컬레이션
-   흔한 장애 증상과 확인 순서
-   재시작·재처리·복구 절차
-   데이터 유실 또는 중복 위험
-   장애 후 검증 및 사후 분석 절차

장애 대응 문서는 단순히 "로그를 확인한다"라고 쓰지 말고, 어디서 어떤
필드와 지표를 확인하고 다음에 어떤 조치를 취할지 단계별로 작성한다.

### 4.17 ADR·기술 부채·변경 영향

ADR(Architecture Decision Record)에는 다음을 기록한다.

-   제목과 상태
-   결정이 필요한 배경
-   고려한 대안
-   결정 내용
-   장점·단점 및 트레이드오프
-   영향을 받는 컴포넌트
-   결정일과 관련 담당자
-   재검토 조건

변경 영향도 문서에는 기능 변경 시 영향받을 API, DB, 이벤트, 권한, 외부
시스템, 테스트, 대시보드 및 운영 절차를 연결한다.

### 4.18 문서 운영 정책

-   문서 소유자와 검토자
-   문서의 기준 경로
-   소스와 문서의 연결 방식
-   변경 시 문서 갱신이 필요한 조건
-   자동 생성과 수동 작성의 구분
-   링크 및 다이어그램 검사 방법
-   실행 명령 검증 방법
-   오래된 문서의 표시와 폐기 기준
-   마지막 검증 커밋과 검증 날짜

## 5. 다이어그램 카탈로그

필요한 다이어그램을 선택한다. 모든 프로젝트에 모든 다이어그램이 필요한
것은 아니다.

  목적          권장 다이어그램
  ------------- ------------------------------------------
  시스템 이해   System Context, C4 Container
  아키텍처      Component, Package, Layered Architecture
  도메인        Domain Model, Aggregate 관계, ERD
  기능 탐색     Feature Map, Use Case, User Journey
  업무 처리     Activity Diagram, BPMN, Flowchart
  호출 추적     UML Sequence, Communication Diagram
  상태 변화     State Machine, State Transition
  데이터 처리   Data Flow, ETL Flow
  비동기 처리   Event Flow, Message Sequence
  API 관계      API Dependency Map, OpenAPI
  인프라        Deployment Diagram, Network Topology
  배포          CI/CD Pipeline, Release Flow
  보안          Trust Boundary, Authentication Flow
  장애 대응     Failure Flow, Retry/Compensation Flow
  데이터 변경   Migration Flow, Data Lifecycle
  운영          Observability Flow, Alert Escalation

### 다이어그램 품질 기준

-   제목, 목적, 범위를 표시한다.
-   기호와 용어를 일관되게 사용한다.
-   중요한 노드와 연결이 실제 코드·설정에 근거해야 한다.
-   동기 호출과 비동기 이벤트를 구분한다.
-   오류·재시도·보상 처리가 중요하면 표현한다.
-   지나치게 큰 그림은 시스템·모듈·기능 수준으로 나눈다.
-   다이어그램 원본은 가능하면 버전 관리가 가능한 텍스트 형식으로
    보관한다.
-   다이어그램이 소스와 달라질 수 있으므로 생성 시점과 근거를 추적한다.

## 10. 문서 생성 워크플로

먼저 0절에 따라 입력·출력 모드·사용할 내부 자원을 확인한다. 각 단계의
근거와 검증 결과를 누적하고 확정되지 않은 운영 정보는 확인 필요로 남긴다.

### 1단계: 저장소 인벤토리 작성

최상위 파일, 모듈, 빌드 도구, 설정, 테스트, 배포 및 IaC 파일을 파악한다.

### 2단계: 실행 경로 검증

진입점, 빌드 명령, 테스트 명령, 로컬 실행 방법을 찾아 검증한다. 검증할
수 없다면 실행 성공을 주장하지 않는다.

### 3단계: 시스템과 도메인 모델 작성

컨텍스트, 컨테이너, 모듈 관계, 데이터 모델, 용어 사전을 작성한다.

### 4단계: 기능 카탈로그 작성

API, 이벤트, 스케줄러, UI 등 진입점을 기준으로 기능을 분류한다. 기능과
소스 파일을 연결한다.

### 5단계: 핵심 기능 추적

각 기능의 호출 경로, 비즈니스 규칙, 데이터 접근, 외부 연동, 오류 처리,
테스트를 추적한다.
분석 범위에 기능 변경이 포함되면 대표 기능 하나에 대해 수정할 파일,
영향받는 API·DB·이벤트, 실행할 테스트와 예상 결과를 연결한 첫 변경
가이드를 작성한다. 문서 요청만으로 대상 애플리케이션 코드를 수정하지 않는다.

### 6단계: 다이어그램 작성

시스템 수준 다이어그램부터 시작해 핵심 기능의 플로우와 시퀀스
다이어그램을 작성한다.

### 7단계: 개발·배포·운영 문서 작성

로컬 환경, 빌드, 테스트, CI/CD, 배포, 롤백, 관측성, 장애 대응을
작성한다.

### 8단계: 근거 검토

클래스명, 경로, 설정 키, API, 명령, 인프라 리소스가 실제 저장소와
일치하는지 확인한다.

### 9단계: 실행·링크 검증

가능한 명령과 테스트를 실행하고 내부 링크 및 다이어그램을 확인한다.
검증하지 못한 항목은 상태를 명시한다.
HTML 모드는 0.6절의 내장 검증 도구와 UI 확인을 수행하고 모든 템플릿
예시 데이터가 실제 분석 내용으로 교체되었는지 확인한다.

### 10단계: 문서 유지보수 연결

기능·API·DB·인프라 변경 시 갱신해야 할 문서를 정하고, CI 검사나 MR
체크리스트에 연결한다.

## 11. 품질 검토 체크리스트

### 정확성

-   [ ] 분석 기준 저장소·커밋·날짜·범위와 작업 트리 변경 여부가 기록되었다.
-   [ ] 판단 상태와 실행 검증 결과가 구분된다.
-   [ ] 설명된 파일과 클래스가 실제 존재한다.
-   [ ] API와 설정 이름이 실제 코드와 일치한다.
-   [ ] 추론과 확인된 사실이 구분된다.
-   [ ] 미검증 명령을 검증된 것으로 표현하지 않는다.
-   [ ] 운영 구성과 로컬 구성의 차이를 구분한다.

### 완결성

-   [ ] 신규 개발자가 프로젝트 목적을 이해할 수 있다.
-   [ ] 로컬 실행과 테스트 방법을 찾을 수 있다.
-   [ ] 핵심 기능의 진입점부터 데이터 저장까지 추적할 수 있다.
-   [ ] 주요 예외와 외부 의존성을 이해할 수 있다.
-   [ ] 배포·검증·롤백 절차를 찾을 수 있다.
-   [ ] 운영 장애 시 확인할 위치와 담당 경로를 알 수 있다.

### 유지보수성

-   [ ] 두 형식을 제공한 경우 근거·용어·검증 결과가 일치한다.
-   [ ] 문서 간 링크가 유효하다.
-   [ ] 중복 설명을 최소화하고 기준 문서를 명확히 했다.
-   [ ] 문서가 특정 개인의 지식에만 의존하지 않는다.
-   [ ] 소스 변경 시 갱신할 문서가 식별된다.
-   [ ] 다이어그램 원본과 생성 근거를 관리한다.

### 보안

-   [ ] 토큰·비밀번호·개인 키·실제 비밀 값이 없다.
-   [ ] 민감한 내부 주소·계정 식별정보가 정책에 맞게 처리되었다.
-   [ ] 권한 설명에 불필요한 과도 권한이 포함되지 않았다.
-   [ ] 예제 데이터에 실제 개인정보가 없다.

문서를 한 번에 모두 만들지 않는다.

### P0 --- 개발 시작에 필수

-   프로젝트 개요
-   아키텍처 개요
-   레포지토리 구조

-   빌드와 테스트
-   설정과 환경 변수
-   핵심 기능 카탈로그

-   도메인 용어 사전
-   기능별 코드 구조
-   핵심 플로우와 시퀀스 다이어그램
-   API 및 DB
-   외부 시스템 연동
-   오류 처리와 테스트 전략

### P2 --- 배포와 운영에 필수

-   CI/CD와 배포
-   인프라 리소스 매핑
-   로그·메트릭·알람

## 13. 최종 산출물 정의

다음은 전체 범위 요청의 산출물 기준이다. P0 또는 특정 기능만 요청받은
경우 해당 범위에 적용하고 나머지는 후속 작업·해당 없음으로 구분한다.
Markdown에서는 문서 묶음, HTML에서는 같은 역할의 챕터·용어집·근거
목록으로 제공한다.

1.  **진입점 문서**: 프로젝트 개요, 문서 목차, 시작 경로
2.  **아키텍처 문서**: 시스템 경계, 구성 요소, 의존성 및 주요 데이터
    흐름
3.  **기능 카탈로그**: 핵심 기능과 실제 소스 위치의 연결
4.  **도메인 용어 사전**: 업무 용어와 코드 명칭의 매핑
5.  **개발 가이드**: 환경 구축, 빌드, 실행, 테스트
6.  **핵심 기능 문서**: 구조, 업무 플로우, 시퀀스, 오류 및 테스트
7.  **배포·운영 가이드**: 환경별 설정, 배포, 검증, 롤백, 관측성
8.  **검증 정보**: 근거 파일, 테스트·명령 검증 결과, 미확인 사항
9.  **유지보수 정책**: 문서 소유자, 갱신 조건, 검증 절차

모든 문서가 존재하는 것 자체가 완료 기준은 아니다. 문서가 실제 소스에
근거하고, 신규 개발자가 핵심 작업을 수행할 수 있으며, 불확실한 부분이
명확히 표시되어 있어야 한다.

## 14. 작성 시 최종 원칙

-   문서는 저장소의 실제 구조와 기술 스택을 따라간다.
-   확인할 수 없는 업무 의미와 운영 절차는 추측하지 않는다.
-   설명은 추상적인 개념보다 실제 파일 경로와 실행 가능한 절차를
    우선한다.
-   핵심 기능은 업무 관점과 코드 관점을 함께 설명한다.
-   다이어그램은 이해를 돕는 도구이며 실제 코드의 대체물이 아니다.
-   비밀정보와 개인정보를 문서화하지 않는다.
-   자동 생성된 문서는 근거와 검증 상태를 남긴다.
-   문서의 정확성, 실행 가능성, 갱신 가능성을 최종 품질 기준으로 삼는다.
